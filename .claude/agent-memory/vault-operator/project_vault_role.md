Single-node Vault OSS deployment managed by Ansible role at `tarnished_lab/roles/vault/`.

Key facts:
- Target: single-node VPS, Linux/systemd, Vault 1.21.2, Integrated Storage (Raft)
- Scope: KV v2 only (`secret/` mount). PKI commented out.
- TLS: self-signed cert generated by the role via openssl on first run (creates: guard)
- Unseal: manual Shamir (5 shares, threshold 3) — NOT auto-unseal
- Auth method for automation: root token read from disk (security concern)

**Why:** Home-lab infrastructure project ("tarnished_lab"), production-grade hardening desired.
**How to apply:** Flag root-token-on-disk pattern and manual unseal as the two most important production gaps to address in future work.

Known issues audited 2026-04-14:
- Directory permissions set to 0777 (should be 0750/0700)
- Config file deployed as 0777 (should be 0640 vault:vault)
- Systemd unit deployed as 0677 (should be 0644 root:root)
- Audit block in config.hcl.j2 is not valid HCL (not how audit devices are configured in Vault)
- Config deployed as config.hcl but service and ConditionFileNotEmpty reference vault.hcl
- retry_join in raft storage is unnecessary/misleading on a single-node cluster
- vault_version "1.21.2" does not exist as of knowledge cutoff (latest 1.x is ~1.19.x); likely should be 1.19.x
- Root token persisted on server AND fetched locally in plaintext
- Unseal keys stored on server in /etc/vault.d/keys/ — same host as Vault data
- kv.yml uses root token for all API calls; no least-privilege token/AppRole created
- init.yml fetch task has `delegate_to: inventory_hostname` which is a no-op/redundant
- vault_unseal_keys_dir is under vault_config_dir (/etc/vault.d/keys) — not a separate restricted path
- ProtectSystem=full in systemd unit conflicts with Vault needing to write to /etc and /opt
